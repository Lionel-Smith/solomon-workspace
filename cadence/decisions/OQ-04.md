# OQ-04 — WhatsApp dispatch method

**Source:** `solomon-docs/plans/HFS_CADENCE_LAYER_PLAN_FINAL.md` §6
**Gates:** `ROUTINE-02` (news), `ROUTINE-03` (standup), `ROUTINE-06` (energy retro), `INT-01` (Twilio webhook adapter)
**Gating wave:** 1
**Decided:** 2026-05-25
**Decision:** **Accept plan default — Routine connector if available by Phase 3, else Samson cross-post fallback.**

## Resolution

1. **Primary path (preferred):** Native WhatsApp connector inside the Claude Code Routine.
   - Each affected Routine prompt instructs Claude to call the WhatsApp connector directly (post message, wait for reply via the energy-retro flow).
   - Samson sees the dispatched-to evidence in `output_artifacts.connector_calls` during ingestion.

2. **Fallback path (Phase 3 decision point):** If Anthropic has **not** shipped a WhatsApp connector by the start of Phase 3 (Wave 7, `ROUTINE-10`):
   - Routines post the digest to Slack only.
   - Samson `whatsapp_handler` cross-posts the Slack message body to Twilio WhatsApp Business API on receipt of the Slack message (via `chat.postMessage` event sub).
   - `INT-01` ships the Twilio adapter regardless (still needed for inbound `learn:`, `energy:`, `approve <id>`, `reject <id>` parsing).

## Decision deadline

`ROUTINE-10` (Wave 7) is the no-going-back checkpoint. Check Anthropic connector inventory before that wave fires; if WhatsApp connector is present, use primary path in `ROUTINE-02/03/06`. If absent, those Routine prompts get a 5-line edit to drop the WhatsApp connector call and Samson takes over.

## Why this matters

- WhatsApp delivery to the founder phone is the single most-load-bearing notification surface (per the research brief "the load-bearing ritual is the one that makes everything else compound"). Reliability cannot regress.
- The primary-then-fallback design means we don't *block* on Anthropic's connector roadmap — the Samson adapter ships in INT-01 anyway because of inbound message handling.
